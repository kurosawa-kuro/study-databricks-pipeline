## 1. 概要

ローカル CSV を **GCS → Cloud Run Job → Databricks Managed Volume → COPY INTO → Table** の順で取り込むパイプライン。

```text
ローカル CSV (data/*.csv)
  ── make gcs-upload ─────────────▶ GCS  gs://<bucket>/incoming/*.csv
  ── Cloud Run Job (csv-to-volume) ─▶ Managed Volume /Volumes/workspace/default/raw_csv/
  ── COPY INTO (SQL Warehouse) ─────▶ Table workspace.default.customers
```

前身 `study-databricks-import`(Files API で直接 Volume → `read_files()` + MATERIALIZED VIEW)を拡張し、前段に GCS + Cloud Run、最終段に COPY INTO での実テーブル取込を足した後継。

**設計の肝**: Databricks Free Edition は GCS を external volume として直接マウントできない。そのため **Cloud Run Job (`csv-to-volume`) が「GCS DL → Files API PUT」を仲介** して Managed Volume へ載せる。

## 2. 対象 / 非対象

### 対象

- Databricks **Free Edition のみ**
- Serverless SQL Warehouse
- Managed Volume(`workspace.default.raw_csv`)
- Files API(`PUT /api/2.0/fs/files`)
- COPY INTO による実テーブル取込
- GCS(取得元)
- Cloud Run Jobs(GCS → Volume 転送エージェント)
- Artifact Registry / Secret Manager(Cloud Run 運用)

### 非対象

- Databricks Free Trial / 有償 workspace / 管理者権限前提の構成
- Databricks Connect 主導の開発
- GCS external location / external volume(Free Edition で作れない → Cloud Run で仲介)
- catalog は常に **`workspace` 固定**(Free Edition の制約)

> spec の対象/非対象は厳守する。ここに無い機能(auth/UI/REST 化、複数テーブル汎用化など)は勝手に追加しない。

## 3. アーキテクチャ確定仕様

実行経路は **3 本** に落ちる。

| 経路 | 入口 | 中継 | 本体 | 認証 |
|---|---|---|---|---|
| **SQL 経路** | `make sql-* / volume-create / volume-clean / table-*` | `scripts/databricks_sql_test.sh` | `src/sql_connectivity.py`(`databricks-sql-connector`) | `DATABRICKS_TOKEN`(= `DWH_DATABRICKS_TOKEN`) |
| **Files API 経路** | `make volume-upload`(Phase 1) | — | `scripts/databricks_volume_upload.sh`(curl PUT) | `DATABRICKS_FILES_TOKEN` |
| **GCP 経路** | `make gcs-* / secret-create / job-deploy / job-run` | `scripts/{gcs_upload,deploy_cloudrun_job,run_cloudrun_job}.sh` | Cloud Run Job 内 `src/volume_uploader.py` | `gcloud auth` + Secret Manager `databricks-pat` |

```text
[SQL 経路]   Makefile ─▶ databricks_sql_test.sh ─▶ src/sql_connectivity.py ─▶ SQL Warehouse
[Files 経路] Makefile ─▶ databricks_volume_upload.sh (curl) ─────────────▶ Files API ─▶ Volume
[GCP 経路]   Makefile ─▶ gcloud (GCS / AR / Cloud Run / Secret Manager)
                          └─ Cloud Run Job ─▶ src/volume_uploader.py ─▶ GCS DL → Files API PUT ─▶ Volume
```

CSV を Volume へ載せる手段は 2 通り(どちらも結果は同じ Volume 着地):

- **Phase 1**: `volume-upload`(ローカル → Files API で直接)。GCS / Cloud Run なしで検証する用。
- **Phase 2+**: GCS + Cloud Run Job(本番想定の主導線)。

## 5. 取込仕様(COPY INTO)

[table/02_copy_into_from_volume.sql](../databricks/sql/table/02_copy_into_from_volume.sql):

- Volume 上の `customers.csv` を `customers` テーブルへ取り込む。
- `FILEFORMAT = CSV` / `FORMAT_OPTIONS ('header' = 'true')`。
- CSV は型情報を持たないため各列を **明示 CAST**(`CAST(... AS INT/STRING/DATE)`)。
- **冪等性**: COPY INTO は取込済みファイルを記録するため、再実行しても重複行を作らない。
  - 1st: `num_inserted_rows = 3` → `row_count = 3`
  - 2nd: `num_inserted_rows = 0` → `row_count = 3` 維持

> 注意: 既存の VALUES seed(`sql-values` / `foundation`)で `customers` が既に 3 行ある状態で COPY INTO すると `row_count = 6` になる。クリーン計測時は table を drop してから取り込む。

## 7. 認証・Secret 仕様

| 実行環境 | 認証 | 管理方法 |
|---|---|---|
| ローカル(SQL / Files API) | `DWH_DATABRICKS_TOKEN`(`sql, files` の両 scope を持つ scoped PAT) | Doppler `kuro-dev-k/dev`、`doppler run --` 前置 |
| Cloud Run Job | Secret Manager `databricks-pat` → env `DATABRICKS_FILES_TOKEN` として mount | `make secret-create`(doppler 経由で token 注入) |
| GCP 操作 | `gcloud auth`(kurosawa8122@gmail.com) | gcloud CLI(doppler 不要) |

- `DATABRICKS_TOKEN` は `DWH_DATABRICKS_TOKEN` を参照。`DATABRICKS_FILES_TOKEN` は `DWH_DATABRICKS_FILES_TOKEN` があればそれ、無ければ `DWH_DATABRICKS_TOKEN` にフォールバック。
- **token scope に注意**: upload(`files` scope)が 403 等で失敗する場合は PAT の scope を疑う。
- Cloud Run 実行 SA(既定 `<projectNumber>-compute@developer.gserviceaccount.com`)に必要なロール(`deploy_cloudrun_job.sh` が冪等付与):
  - `roles/secretmanager.secretAccessor`(secret `databricks-pat`)
  - `roles/storage.objectViewer`(bucket)
- **PAT 運用**: Free Edition の PAT はローテーション推奨。Doppler の secret は参照が基本で、自分から削除はしない。
