# 学習検討: 次にやるべき学習の方向性

> 実装済みの土台(GCS → Cloud Run Jobs → Managed Volume → Table)を前提に、次の学習方向を「Databricks 資格向け」と「ML/MLOps 実務向け」の 2 本立てで整理したメモ。

## 結論

次にやるべき学習は **2 本立て** が正解。

| 方向性 | 次にやるべきこと | 目的 |
|---|---|---|
| ① Databricks 基礎資格向け | Delta Lake / Spark SQL / Workflows / Unity Catalog / DLT 基礎 | Databricks Certified Data Engineer Associate 対策 |
| ② ML・MLOps 実務向け | MLflow / Feature Engineering / Model Registry / Batch 推論 / 評価ログ / 再学習パイプライン | ML/MLOps 案件で使える Databricks 化 |

今の実装はすでに次まで通っている:

```text
ローカル CSV
  → GCS
  → Cloud Run Jobs
  → Databricks Managed Volume
  → Databricks Table
```

Free Edition 制約を Cloud Run 転送エージェントで回避する構成で、単なる Databricks 入門ではなく **外部 GCP 基盤から Databricks へデータを流し込む最小データパイプライン**。ここから先は「資格用に Databricks の標準機能へ寄せる学習」と「ML/MLOps 実務に接続する学習」を分けた方がよい。

## 理由

- Data Engineer Associate は、Databricks 公式でも試験ガイド確認・関連トレーニング・ギャップ埋めを推奨。
- Machine Learning Associate は Databricks 上で基本的な ML タスクを行えることを問う資格で、MLflow・特徴量・学習・評価・デプロイ寄り。

同じ Databricks でも見る場所が違う。

| 観点 | Data Engineer Associate 寄り | ML/MLOps 寄り |
|---|---|---|
| 主戦場 | Lakehouse / Delta / SQL / Pipeline | MLflow / Feature / Model / Evaluation |
| データ | Bronze/Silver/Gold | Training / Validation / Inference |
| 成果物 | 安定したテーブル更新 | 再学習・推論・モデル管理 |
| 既存実装との接続 | COPY INTO 後の Delta 運用 | customers table を特徴量・推論入力にする |

今の実装では COPY INTO による実テーブル取り込みと冪等性まで意識されており(処理済みファイルを記録するため再実行で重複行を作らない)、資格・実務どちらにも使える土台になっている。

## 有力シナリオ

### シナリオ A: まず資格優先なら Data Engineer Associate 方向

次の順番がよい:

1. COPY INTO 後の Delta Table 操作
2. Bronze / Silver / Gold 構成
3. Spark SQL / DataFrame 基礎
4. Databricks Workflows
5. DLT / Lakeflow Declarative Pipelines 基礎
6. Unity Catalog 概念
7. 権限・Catalog・Schema・Table の整理

今のプロジェクトに足すなら:

```text
GCS incoming/customers.csv
  ↓
Managed Volume
  ↓
Bronze table: raw_customers
  ↓
Silver table: cleaned_customers
  ↓
Gold table: customer_features
```

やるべき実装はまずこれ:

```sql
CREATE TABLE workspace.default.raw_customers (...);

COPY INTO workspace.default.raw_customers
FROM '/Volumes/workspace/default/raw_csv/'
FILEFORMAT = CSV
FORMAT_OPTIONS ('header' = 'true');

CREATE TABLE workspace.default.cleaned_customers AS
SELECT
  customer_id,
  trim(name) AS name,
  cast(age as int) AS age,
  current_timestamp() AS processed_at
FROM workspace.default.raw_customers;

CREATE TABLE workspace.default.customer_features AS
SELECT
  customer_id,
  age,
  CASE WHEN age >= 40 THEN 1 ELSE 0 END AS is_middle_age
FROM workspace.default.cleaned_customers;
```

資格向けの本質は **Databricks 上でデータをどう整流化するか**。今の土台は「外から Databricks に入れる」ところまでなので、次は「Databricks 内で Lakehouse らしく変換・管理する」が自然。

### シナリオ B: ML/MLOps 優先なら MLflow + Feature + Batch 推論方向

ML/MLOps に効かせるなら、資格範囲よりも実務 ROI が高い:

1. Gold table を特徴量テーブルにする
2. Databricks Notebook or Job で LightGBM / sklearn 学習
3. MLflow Tracking に metrics / params / model を記録
4. Model Registry に登録
5. Batch 推論結果を prediction table へ保存
6. 評価ログを Delta table 化
7. 再学習条件を Databricks Workflows で管理

実装フロー:

```text
workspace.default.customer_features
  ↓
train.py
  ↓
MLflow Tracking
  ├─ params
  ├─ metrics
  ├─ artifacts
  └─ model
  ↓
Model Registry
  ↓
batch_predict.py
  ↓
workspace.default.customer_predictions
```

GCP MLOps 文脈に寄せると、次の比較軸を持てる(案件で強い):

```text
GCP 側:       Cloud Run Jobs / GCS / BigQuery / Vertex AI
Databricks 側: Delta Table / MLflow / Feature Engineering / Workflow / Model Registry
```

- 「Vertex AI でやるべきか、Databricks でやるべきか」
- 「BigQuery 中心か、Lakehouse 中心か」
- 「Feature Store を入れる価値があるか」
- 「Redis 配信基盤がある場合、Databricks の役割はどこか」

## 破綻条件

### 資格向け学習が破綻する条件

| 破綻条件 | 理由 |
|---|---|
| GCS / Cloud Run / GCP 連携ばかり深掘りする | Databricks 資格の主戦場から外れる |
| Files API 転送の改善ばかりする | Databricks の Lakehouse 理解が増えにくい |
| MLflow に進みすぎる | Data Engineer Associate 対策から逸れる |
| Free Edition 制約回避ばかりになる | 資格で問われる標準構成とズレる |

資格目的なら GCP 連携はもう十分。次は Databricks 内の標準機能へ寄せるべき。

### ML/MLOps 向け学習が破綻する条件

| 破綻条件 | 理由 |
|---|---|
| SQL 変換だけで終わる | ML/MLOps の価値に届かない |
| Notebook で手作業学習して終わる | 再現性・運用性が弱い |
| MLflow Tracking だけで止まる | 実務では Registry / 推論 / 評価まで必要 |
| Feature table を作らない | Databricks で ML をやる意味が薄い |
| GCP Vertex AI との比較軸を持たない | 強みである技術選定力に接続しない |

ML/MLOps 目的なら、モデルを 1 回学習することではなく、**データ → 特徴量 → 学習 → 登録 → 推論 → 評価の状態遷移を作る**ことが本命。

## 実務・行動への影響(おすすめの順番)

### Step 1: 資格向けに Bronze / Silver / Gold を作る

今の customers 単体テーブルを最低 3 層に分ける:

```text
raw_customers
cleaned_customers
customer_features
```

これは Data Engineer Associate 対策と ML/MLOps 土台の両方に効く。

### Step 2: Databricks Workflows で動かす

今は Makefile / Cloud Run Job / SQL 実行が主導線だが、次に Workflows を触るべき:

```text
Task 1: COPY INTO raw
Task 2: transform silver
Task 3: build gold/features
Task 4: verify row count
```

これで資格向けの「Databricks 上のジョブ運用」感が出る。

### Step 3: MLflow で最小 ML パイプライン化する

その後、customer_features を入力に最小モデルを作る:

```text
customer_features
  ↓
train_model.py
  ↓
MLflow Tracking
  ↓
Model Registry
  ↓
batch_predict.py
  ↓
customer_predictions
```

モデルは何でもよい。重要なのは精度ではなく、**Databricks で ML ライフサイクルを回せる状態**。

### Step 4: Vertex AI との比較メモを作る

キャリア上かなり重要。今後の案件でそのまま提案材料になる。

```text
Databricks でやる場合
- Delta Table 中心
- MLflow 中心
- Lakehouse 内で特徴量・学習・推論を寄せやすい

Vertex AI でやる場合
- GCP ネイティブ
- BigQuery / Vertex Pipelines / Feature Store / Model Registry
- 既存 GCP 基盤との親和性が高い
```

## 最終判断(優先順位)

| 優先 | 学習 | 理由 |
|---|---|---|
| 1 | Bronze/Silver/Gold + Delta Table | 資格にも ML にも共通土台 |
| 2 | Databricks Workflows | Databricks らしい運用理解に直結 |
| 3 | MLflow Tracking / Registry | ML/MLOps 実務に直結 |
| 4 | Batch 推論結果を Delta Table 保存 | 実案件の MLOps 感が出る |
| 5 | Feature Engineering / Feature Store 概念 | Vertex AI との比較材料になる |
| 6 | DLT / Lakeflow | 資格・実務の上乗せ |
| 7 | Streaming | 後回しでよい |

結論として、次は **「Data Engineer Associate 向けに Lakehouse 基礎を固め、その直後に MLflow で ML/MLOps 化」** が最もよい。GCP → Databricks 取込済みデータを Delta Lakehouse 化し、MLflow でモデル運用まで持っていくのが最もキャリア価値が高い。
